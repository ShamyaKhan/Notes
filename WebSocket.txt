Polling:
-> browser constantly checks the server every few seconds just in case something changed
-> every time it's a full http request with a bunch of headers to get a tiny response

Protocol:
-> a set of rules for how two computers communicate
-> http is a request-response protocol, great for websites, APIs, loading pages
-> for real-time, we need a protocol that supports a permanent two-way connection
-> websocket connection stays open, so both client and server can send messages anytime
-> it is called full duplex, both sides can talk at the same time
-> persistent full duplex tunnel
-> server can push updates the instant they happen 
-> typing indicators, live comments, multiplayer movements, notifications
-> less expensive because once the connection is open, messages are tiny
-> efficient for servers because servers do not have to handle thousands of http request opening and closing
-> rather thousands of websocket connections sit idle
-> better for mobile because polling wakes up the phone over and over again
-> a single open connection is easier on battery 

WebSocket Handshake:
-> starts as a normal http request
-> then browser adds a special header to upgrade connection to websocket
-> if server supports, it replies with http101: switching protocols
-> it creates a websocket tunnel - open, persistent, real-time
-> websocket has two modes, ws:// unencrypted and wss:// encrypted


WebSocket Connection Lifecycle:
-> it has stages
-> (I) Connect: 
  - setup the socket on a specific port
-> (II) Upgrade/Switch: 
  - browser sends http get request with a special header to upgrade connection to websocket 
  - if server supports, it replies with http101: switching protocols
-> (III) State/Memory: 
  - http is stateless but websocket is stateful
  - server holds a reference to your socket in memory
  - that's how it pushes data instantly
  - it creates a problem - ghost connection (looses wifi, phone dies, close laptop without properly disconnecting)
  - the server thinks connection is still alive, it keeps holding the socket in memory
  - if you don't clean ghost connections, your server eventually dies 
  - to solve this, websocket uses heartbeat / ping-pong
  - server sends a tiny ping (heartbeat) and client responds with a pong (acknowledgement)
  - periodic ping-pong messages ensure the connection remains active and detect dropped connections
  - if the server stops hearing pong, it terminates the socket
  - ping-pong is massively lighter, cheaper and easier on battery


Data Transfer:
-> two main types: text (JSON) and binary (raw bytes)
-> most real-time apps send JSON
-> typing indicators, new message, score update, notification receive
-> socket.send(JSON.stringify({userId: 42, status: "typing"}))
-> binary data is used for audio straming, video frames, multiplayer game states, large payloads
-> you send raya bytes using ArrayBuffer or Blob
-> it's faster, smaller, more efficient
-> how does server know which data type is it?
-> at low level, websocket uses opcode (a label that says this frame is text/binary/closing/ping-pong)

Backpressure:
-> what happens if server sends updates like crazy but the client is on a slow internet connection
-> new messages start piling up in memory
-> production apps monitor how much data is buffered
-> if it's too high they slow down the sending rate so the server does not explode

Choosing WebSocket:
-> socket.io
  - full management suite on top of websocket
  - reconnects, rooms, fallbacks, whole package
  - heavier. if you ship extra client code every message comes with extra overhead 
  - great for speed-up development
-> websockets as service tools
  - pusher, ably
  - easiest path to production
-> ws
  - node js websocket library
  - fast with minimal overhead
  - matches browsers websocket API


WebSocket State Machine:
-> actions are only valid in certain states
-> CONNECTING - OPEN - CLOSING - CLOSED
-> connect() - send()/receive() - close()
-> 0. Connecting: handshake is still happening, don't send yet
-> 1. Open: the tunnel is live, you can send
-> 2. Closing: connection is shutting down, stop pushing data
-> 3. Closed: it's dead, time to reconnect, check using socket.readyState()

Client-side Events:

-> message. you receive server updates, you can parse incoming data and display it
-> close. it means disconnected

How to connect to a websocket:
(I) Initiate the handshake
-> const socket = new WebSocket('ws://localhost:3000')
-> the moment it executes, browser creates a TCP connection with the server
-> sends an http get request with an upgrade websocket
-> and waits for 101 switch protocol response
-> the connection is not ready yet
-> the socket exists immediately but it's not usable until the open event fires


Why use socket.addEventListener() instead of socket.onmessage() or something like that?
-> addEventListeners allow for multiple listeners
-> socket.onsomething only allows for one
-> you often want multiple independent reactions like logging, analytics, UI updates on the same web event
-> websockets are event-driven, not request-driven
-> socket.addEventListener("open", () => {}) event fires only once when the http websocket upgrade succeeds
-> the protocol is officially switched and tunnel established
-> this is the first safe moment to call socket.send()
-> socket.addEventListener("open", () => {}) is fired when server intentionally closes the connection or 
   network drops or socket.close() is called
-> once closed,  the socket can never re-open again
-> socket.addEventListener("message", (event) => {}) is fired everytime the server pushes data to the client
-> the server decides when messages arrive
-> event.data can be string, most commonly json or a blob or an array buffer


** once open log appears, http protocol has been deleted from memory
** you are communicating through persistent TCP stream


Socket Patterns:
-> in production, the real skill is designing the message flow
-> when you write socket.send(""), you're sending a blind packet
-> the server receives it and it has zero context
-> is this about a chat message, a typing event, a command or a delete request
-> we fix that with structure


Envelope Pattern:
-> in real-time apps, you don't send raw strings
-> you send a message that includes intent
-> {
     type: "CHAT_MESSAGE",
     id: "uuid-123",
     payload: { text: "Hey everyone", roomId: "general" },
     metadata: { sentAt: "1705622400" }
   }

-> type tells the server what login to run
-> id lets you track the message
-> payload is the actual data
-> metadata includes optional context
-> now your server becomes a switchboard
-> it looks only at one field and instantly routes the action
-> as soon as you parse the message, you open up a literal JS switch statement, check the type and depending on it, 
   you immediately handle within your application

-> socket.on("message", (raw) => {
     const msg = JSON.parse(raw.toString())
     switch(msg.type){
     	case "CHAT_MESSAGE":
	   return handleChatMessage(msg.payload)
	case "TYPING":
	   return handleTyping(msg.payload)
	case "JOIN_ROOM":
	   return handleJoinRoom(msg.payload)
	default:
	   console.log("Unknown Type", msg.type)
     }
   })


Two ways to structure envelope:
(I) Type based commands
-> best when your app has a known list of actions
-> perfect for chat apps, dashboard, collaborative tools
(II) Topic based messages
-> pub sub style
-> best when channels are dynamic
-> perfect for sensors, tickers, live markets and sports engines 


Data Transfer Format:
-> Once the structure is solved, you have to choose a format. JSON or binary
-> Text (JSON) or Binary (raw bytes)
-> JSON is the default, easy, readable, debuggable, flexible and best choice for most apps
-> you want to use binary when messages are of a high frequency 
-> such as GPS updates, mouse movements, audio chunks, game states
-> instead of sending readable texts, you send raw bytes because it takes less bandwidth and latency
-> most serious apps actually use both
-> JSON for control messages, join, auth, commands
-> and binary for high speed data such as movement, audio, sensors
-> when you make the connection and decide which format, you have to move from message structure to message routing


Message Sending Patterns:
(I) Broadcast (one to all):
-> one message goes to every single connected client
-> use case: system announcements, global alerts, service status updates
(II) Unicast (one to one):
-> this is a DM. only one person gets the message
-> you keep a registry where you connect a specific user id to socket
-> without that you would be looping through every client just to find one
-> with a map lookup is instant
-> use case: private messages, user notifications, admin actions
(III) Multicast (one to many):
-> often used to send messages to specific groups
-> it's a group chat pattern, you only send to a specific room
-> use case: dsicord channels, game lobbies, live event chats, collaborative documents


Ackowledgements:
-> websockets are fast, but they are also fire and forget
-> unlike http, there are no 200 automatic OK
-> for critical actions, you add ACKs
-> you send a message with an id, the server processes it and replies with the same id as a receit 
-> if a client does not get the receit in time, retry
-> that's how you add reliability on top of websockets


Pub/Sub Pattern:
-> it's like subscribing to a newspaper
-> you only receive what you actually care about
-> the real challenge is scaling
-> when you have multiple servers, each server only knows its own clients
-> if server 1 publishes an update, server 2 won't know about it
-> to solve this, real systems use message broker


Message Broker:
-> redis
-> the broker becomes the central broadcast layer between all servers
-> that's how you scale to millions of connections


WebRTC:
-> for voice, video and P2P
-> for heavy media like video calls, routing everything through server is expensive and slower
-> web RTC lets two browsers talk directly peer-to-peer with ultra low latency
-> perfect for audio and video
-> only catch is web RTC needs a matchmaking phase
-> two browsers need a way to find each other and exchange connection information
-> that step is called signaling. it is done with websockets
-> the flow will look like this:
-> client A connects to a websocket server and sends an offer for client B
-> client B replies with an answer
-> once they've exchanged network details webRTC connects them directly peer-to-peer
-> the server steps out, media flows directly
-> that's why zoom uses websocket for signaling, chat and join events, but then webRTC for audio/video streaming


WebTransport:
-> for ultra low latency streaming
-> what if peer-to-peer is not possible
-> high fps cloud gaming, live media pipelines, competitive RT systems
-> websockets are built on TCP, one of the primary ways in which we transmitd data on internet
-> TCP has a downside, if one packet gets lost, everything pauses until its resent
-> that's called head-of-line blocking
-> WebTransport fixes this by using http3, powered by QUIC
-> instead of one stream that can freeze, it supports multiple independent streams over a single connection
-> so if one stream gets delayed, the others keep moving
-> that means fewer freezes and smoother real-time delivery
-> unless you're building something insanely latency sensitive, you should stick with websocket


Server-Sent Events:
-> sometimes even websockets are actually overkill
-> if your app only needs one way updates like stock prices, news feeds, live dashboards then SSE is a cleaner tool
-> its basically server pushes updates and client listens
-> no two way messaging, no full-duplex tunnel, just one way stream over http
-> lightweight, simple, reconnects automatically


When do you use what?
-> WebSockets: two way real time apps
    -chat, collaboration, dashboards
-> WebRTC: heavy media, peer-to-peer 
    -voice calls, video calls, file transfers
-> WebTransport: ultra low latency streaming
    - high performance, real-time systems
-> SSE: one way server updates
    - tickers, feeds, streaming data


Real-time systems need to have:
-> stable networking

-> predictable performance
