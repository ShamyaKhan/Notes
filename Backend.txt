How data flow?
-> request starts from our browser
-> first it reaches the dns server
-> in dns server, we define different types of records
-> A record: points to a particular IP
-> C record: points to a particular domain name or subdomain
-> the A record IP address comes from an EC2 instance
-> our request reaches the EC2 instance through this IP
-> before it reaches the particular server/computer, it goes through a firewall (AWS native firewall)
-> the firewall has to allow some kind of request to pass through
-> in the security group of AWS instance, we have to specify what ports we would allow to be accessible over internet
-> SSH port (port range 22) to log into AWS instance through terminals or cmd so we can do different kinds of operations
-> HTTPS (port range 443), HTTP (port range 80) - if we don't allow these two ports, AWS will block it right here
-> after this, our request reaches the computer/server/aws instance
-> then we are using reverse proxy
-> it is a server that sits in front of other servers so that we can manage different types of redirect of config from 
   a centralized space instead of changing configs in every single server
-> for that we are using nginx
-> we are using Certbot to assign SSL certificates automatically
-> it is listening for port 80 in our AWS instance and redirecting request to port 443 which is an https request
-> this part is managed by Certbot
-> what we configure in backend.conf file
-> server_name { backend_demo.sriniously.xyz 
-> whatever request comes to this domain our nginx config will redirect those request to localhost:3001
-> this is the port our node server is running on and this is the final redirection
-> browser - dns - aws - firewall - aws instance - nginx - localhost:3001



Why Backend?
-> any kind of action that deals with data - fetch, receive, persist data
-> browser fetches the html, css, js files one by one and then it paints our window
-> once browser fetches the js files, it hydrates all the event listeners for any kind of interactions
-> the browser is our runtime as it runs all the logic
-> browser runtimes are often sandbox environments, meaning they are isolated from our operating system
-> therefore, the code can access only a limited amount of resources
-> cors is a security policy browsers that restricts JS code to call external APIs, only allowed in the same domain
-> it makes sense because browser is fetching code from a remote server and executing in the user's browser
-> if it's not isolated enough, the remote code can access data or files from user's computer


Why can't we write backend logic in frontend?
-> security - browsers are restrictive, often times a backend needs to access file system (write log file, access env variables)
-> cannot call external APIs unless they have appropriate cors headers, but backend servers often need to connect to other
   servers and fetch data from multiple sources
-> databases - server runtime has access to all native database drivers which allows to communicate efficiently with databases
   these drivers are written to work in environments that can handle socket connections, binary data, maintain persistent
   connections. browsers cannot do this
-> backend servers maintain a list of connections, often known as connection pool to our database server so that it does not have
   to create and destroy connections again and again
-> they receive thousands of requests per second, so they cannot create and destroy connection with each request, otherwise
   database server will get overwhelmed and won't be able to handle the load
-> computing power - frontend applications are everywhere. smartphones, laptops, so the user may not have enough computing power
   to perform heavy business logic


HTTP Protocol:
-> the medium through which our browsers talk to our servers, for both sending and receiving data
-> at the heart of it, there are two main ideas: stateless, client-server model

Stateless:
-> it has no memory of past interactions
-> self-contained: each request carries all the necessary information for the server to process it 
-> such as headers, URL of the resource, methods, cookies, authentication token, session information
-> after the server responds, it forgets about the request
-> if client makes another request, the server treats it as a new and unrelated event
-> benefits
-> simplicity: server does not need to store any information
-> scalability: makes it easy to distribute requests across multiple servers because no server needs to keep
   track of a session and if server crashes, it doesn't affect the state of a client interaction
-> because it is stateless, developers often implement state management techniques like cookies or sessions or tokens
   to maintain continuity in interactions where needed like user logins or shopping carts

Client-Server Model:
-> client is usually a web browser or an application that initiates the communication by sending a request to the server
-> server hosts resources like websites, apis and other contents and it waits for incoming requests from the clients
-> after receiving a request, server processes it and sends appropriate response such as web page, JSON, text, error...
-> https is a secure version of http with more security features like encryption, certificates or TLS
-> at first, client and server need to establish a connection
-> for that, http uses TCP
-> http does not require the underlying transport protocol to be connection based
-> it only requires it to be reliable and not lose messages, at minimum presenting an error in such cases
-> TCP is connection based
-> backend developers deal with application layer of the OSI model

Evolution of HTTP:
-> HTTP/1.1 introduced persistent connection that allow multiple requests and responses over the same TCP connection that
   is established before sending the request. it also introduced chunk transfer encoding and better caching mechanism
-> HTTP/2 introduced multiplexing that allow multiple requests or responses over a single connection
-> it uses binary framing instead of texts
-> it supports header compression with edge pack and server push that allow servers to send resources before client requests them
-> HTTP/3 built on QUIC protocol - a transport layer protocol over UDP
-> it improved performance with faster connection establishment, reduced latency and better handling of packet loss
-> it continues to support multiplexing without head-of-line blocking

HTTP Headers:
-> key-value pairs of different parameters that are sent and received by both client and server
-> contains metadata


Request Headers:
-> helps the server understand the client's environment, preferences, capabilities
-> User-Agent: identifies what kind of client is that, browser or postman or some kind of server or mobile app
-> Authorization: contains credentials like bearer token for the server to identify the user
-> Cookie: 
-> Accept: what type of content we are expecting, JSON or text or html

General Headers:
-> used in both requests and reponses
-> contains some metadata about the message itself
-> Date:
-> Cache-Control:
-> Connection:

Representation Headers:
-> provides information or representation of resource being transmitted such as request body or response message
-> ensures that the client and server knows how to interpret and process the request/response
-> Content-Type: describes the media type of the request or response. it could be JSON or HTML...
-> Content-Length: describes the size of the resource in bytes
-> Content-Encoding: specifies any encoding like G or D-flare
-> ETag: unique identifier, mostly used for caching 

Security Headers:
-> used to enhance the security of request/response
-> controls how the browser behaves with resources and enforces security policies
-> Strict-Transport-Security (HSTS): ensures the client only communicates with the server over https, 
   preventing protocol downgrade attack
-> Content-Security-Policy (CSP): restricts the sources from which contents like JS, CSS or images can be loaded,
   helping prevent cross-site scripting attack
-> X-Frame-Options: prevents the web page from being embedded in iframe mitigating clickjack attack
-> X-Content-Type-Options: ensures that the browser does not try to guess the mime type of the content, 
   preventing mime type sniffing attack 
-> Set-Cookie: with httpOnly or secure flag, secures cookies by making them inaccessible to JS and ensure that
   they are sent over https


Extensibility:
-> http is highly extensible because headers can be easily added or customized without altering the underlying protocol
-> we only have to add some kind of metadata and the whole flow interaction changes depending on that
-> makes http adaptable to new technologies and use cases
-> developers can create custom headers like X-Custom-Header for specific application or their own use cases
-> accept, accept-language, accept-encoding headers allow servers to server different versions of the content, based on
   the client's preference


Remote Control:
-> http headers act as remote control on the server side
-> they allow the client to send instructions or preferences, influencing how the server processes or responds
-> clients can request specific formats using accept header and the server can respond with appropriate header. if the client
   wants html, server sends html, if the client wants JSON, server sends JSON, ....
-> caching and expiration control - the server can use headers like cache-control or expires to control how long a resource
   should be cached by the client
-> authentication - the client can authenticate itself through authorization header, influencing access control decisions
-> these provide various capabilities on top of our messages


HTTP Methods:
-> represents different kinds of actions that a client can request on a server
-> they define the intent of the interaction
-> gives clear semantic meaning to each type of action


Idempotent:
-> the methods which we can call multiple times and get the same result
-> GET, PUT, DELETE: idempotent
-> POST: non-idempotent

Options Method:
-> used in the CORS flow (same origin policy)
-> used to fetch the capabilities of the server for a cross origin request, known as CORS
-> by default browsers follow the same origin policy which restricts webpages from making request to a different domain
-> cors specify who can access their resources and how
-> it controls how web applications interact with resources hosted on a different domain
-> in a cross-origin request there are two types of flows: simple request, pre-flighted request


Simple Request:
-> suppose our frontend is at example.com and server is at api.example.com
-> we make a GET request to the server
-> GET /api/products/123 HTTP/1.1
   Host: api.anotherdomain.com
   Origin: https://example.com
   Accept: application/json

-> server checks for the origin header in the request and if the origin is allowed, the server includes the 
   access-control-allow-origin in the response and sends the resource 

-> HTTP/1.1 200 OK
   Content-Type: application/json
   Access-Control-Allow-Origin: https://example.com
   {
       "product": {
           "id": 123,
	   "name": "example product",
           "price": 29.99
          }
   }

-> while parsing the response, browser looks for the appropriate cors header. if the access-control-allow-origin contains is there
   and it contains our domain, the browser lets the response go through client or allows the JS client read the response
-> otherwise if the access-control-allow-origin is missing, the browser will not allow JS code to read the response


Pre-flighted Request:
-> the browser checks three conditions before it decides it has to do a pre-flighted request
-> it has to inquire some capabilities before the original request to let the server know about them
-> when does a request qualify as a pre-flighted request?
-> first condition is, it has to be a cross-origin request
-> then, it has to fall under either one of the three conditions 
-> the method is not GET/POST/HEAD (eg, PUT, DELETE)
-> the request includes non-simple headers (like Authorization, X-Custom-Header)
-> the request has a Content-Type other than application/x-www-form-urlencoded, multipart/form-data, or text/plain
-> a pre-flighted request is made with the http method: options

-> OPTIONS /api/resource/ HTTP/1.1
   Host: api.anotherdomain.com
   Origin: https://example.com
   Access-Control-Request-Method: PUT   // asking the server whether this method is supported for this route or not
   Access-Control-Request-Headers: Authorization   // whether the server supports this header or not if needed

-> the browser sends the options request to the server
-> the request does not include any data or request body
-> it's just a general inquiry to the server about it's capabilities
-> after that, if the server supports cross origin request, it will send response like this
-> otherwise the request will be blocked by the browser

-> HTTP/1.1 204 No Content
   Access-Control-Allow-Origin: https://example.com
   Access-Control-Allow-Methods: PUT, DELETE
   Access-Control-Allow-Headers: Authorization
   Access-Control-Max-Age: 86400   

-> access-control-max-age means, the response will be same for this much time, you don't need to make any more
   pre-flighted request before you send the original request for this route
-> then the browser sends the original request

-> PUT /api/resource HTTP/1.1
   Host: api.anotherdomain.com
   Origin: https://example.com
   Authorization: Bearer token123
   Content-Type: application/json
   {
       "name": "John Doe"
   }

-> then the server responds according to the original request

-> HTTP/1.1 200 OK
   Access-Control-Allow-Origin: https://example.com
   Content-Type: application/json
   {
      "message": "Resource updated successfully"
   }
